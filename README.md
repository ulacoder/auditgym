# AuditGym: RL-среда для ИИ-аудитора

**Трек FinTech, Genesis Hackathon 2026. Команда Tech Jacket.**

Воспроизводимый симулятор для дообучения моделей финансового аудита. Генератор создаёт
синтетическую компанию за один отчётный период: книгу проводок, счета, платежи и курсы.
В эти данные внесены скрытые ошибки с записанной причиной. Агент исследует записи через узкий
набор инструментов и отправляет выводы с доказательствами. Оценщик сопоставляет выводы с
эталоном и выдаёт терминальную награду.

Ядро написано на чистом Python 3.11 и использует только стандартную библиотеку. Сеть, GPU и
платные API не нужны. Один эпизод генерируется примерно за 0,05 с.

---

## Запуск одной командой

```bash
# Docker (официальная проверка без сети)
docker build -t auditgym:1.0.0 .
docker run --rm --network none --cpus 2 --memory 4g auditgym:1.0.0

# или локально (Python 3.11+)
pip install -r requirements.txt
python -m auditgym check
```

Команда `check` выполняет четыре шага и завершается с кодом 0 только при полном успехе:

1. `pytest`: 74 теста среды, сопоставления, награды, изоляции и генератора.
2. Валидация данных и эталона для всех эпизодов train, dev и holdout_example.
   Проверяются бухгалтерские равенства до и после внесения ошибок, отсутствие расхождений до
   ошибок, независимое воспроизведение каждой объявленной ошибки из открытых записей, наличие
   доказательств и схемы. Отдельно сверяется отпечаток данных: SHA-256 всех таблиц и эталонов
   совпадает с `configs/FINGERPRINT`.
3. Четыре базовые политики организаторов и наша скриптовая политика на 20 эпизодах в духе
   закрытого набора: 5 чистых, 5 с взаимодействующими ошибками, 10 смешанных. Оценщик работает
   в отдельном процессе.
4. 20 парных проверок. Повтор того же seed и тех же действий даёт идентичную траекторию, а
   смена ID и порядка строк сохраняет эталон, ответ oracle и награду.

Отчёт сохраняется в `reports/check_report.md` и `reports/check_report.json`.

Другие команды:

| команда | что делает |
|---|---|
| `python -m auditgym demo` | показ работы среды: скриптовая политика проходит эпизод шаг за шагом |
| `python -m auditgym evaluate --split dev` | P, R, F1, возврат, шаги и время для политик на сплите |
| `python -m auditgym export` | выгружает 10 train и 10 dev эпизодов в `episodes/`, файлы оценщика в `grader_data/` |
| `python -m auditgym trajectories` | пишет `trajectories/trajectories.jsonl` (режим train) |
| `python -m auditgym serve --mode eval --grader-log g.jsonl` | изолированный сервер среды (JSON-строки по stdin/stdout) |

## Контракт среды

```python
from auditgym import AuditEnv
env = AuditEnv(mode="train")            # "eval": награда и диагностика остаются у оценщика
obs, info = env.reset(seed=1, config={"errors": {"fx_conversion": 2}})
obs, reward, terminated, truncated, info = env.step(
    {"tool": "list_records", "args": {"table": "ledger", "cursor": None, "limit": 50}})
```

Контракт JSON-совместимый, в стиле Gymnasium. Наследование от `gymnasium.Env` не требуется.

**Первое наблюдение** содержит задачу, manifest, краткую политику (`policy.json`), список
инструментов и остаток бюджета.
**Наблюдение шага** имеет вид `{step, steps_remaining, tool, result, error}`. В нём только
запрошенные записи или результат, либо ограниченная ошибка `{code, message}` длиной до 200
символов.

| действие | аргументы | результат |
|---|---|---|
| `list_records` | `table` ∈ ledger, invoices, payments, fx; `cursor`; `limit` от 1 до 50 | `records`, `total`, `next_cursor` (стабильный курсор `table@offset`) |
| `get_record` | `table`, `id` (row_id / invoice_id / payment_id / `DATE:SRC:TGT` для fx) | `record` |
| `get_document` | `doc_id` | `doc_type`, `document` |
| `calculator` | `expression` | `value`. Только десятичная арифметика: `+ - * / // % **` и скобки, без имён и вызовов |
| `submit` | `findings` = `{episode_id, findings:[...]}` | `{accepted}` без подсказок о правильности; эпизод завершается |

Правила эпизода:

- Бюджет 100 шагов, отправка тоже считается шагом. `submit` даёт `terminated=true`. Исчерпанный
  лимит шагов или 60 секунд дают `truncated=true` и оцениваются как пустой ответ.
- Неизвестные ID, таблица, курсор, действие или неверные аргументы возвращают ограниченную
  ошибку и тоже расходуют шаг.
- Награда во время исследования равна 0. Терминальная награда возвращается политике только в
  режиме `train`. В режиме `eval` политика получает 0 и пустой info, а итог читается через
  `grader_result()` или из `--grader-log` серверного режима.
- Записи отдаются копиями только для чтения. Shell, SQL, файловой системы и интернета нет.
- Одинаковые seed, config, версия и действия дают одинаковые записи, переходы и награды.
  `reset` полностью изолирует состояние эпизода.

### Изоляция оценщика

`python -m auditgym serve` поднимает среду и оценщик в отдельном процессе. Процесс агента
видит только наблюдения, а эталон, seed и диагностика туда не попадают. Итог пишется в
`--grader-log`, который агент не читает. Клиент `auditgym.server.RemoteEnv` реализует тот же
`reset`/`step`; именно через него `check` запускает базовые политики.

## Данные эпизода

Эпизод описывает одну компанию за один отчётный период (месяц): около 280–1 820 проводок,
94–180 документов и от 0 до 12 ошибок.

```
episodes/<split>/<name>/
  manifest.json   schema_version, episode_id, base_currency, currency_exponents,
                  period_start/end (end исключительно), timezone, counts, rounding
  ledger.csv      row_id,timestamp,account,debit_minor,credit_minor,currency,entity_id,invoice_id,payment_id
  invoices.jsonl  doc_id,invoice_id,entity_id,issued_at,due_at,currency,total_minor,line_items
  payments.jsonl  doc_id,payment_id,timestamp,currency,amount_minor,invoice_refs
  fx.csv          date,source_currency,target_currency,rate
  policy.json     дата курса, граница периода, округление, правила отчётности, допуски
grader_data/<split>/<name>/     ← закрыто: агент не видит
  truth.json      issue_id,type,affected_ids,expected_amount_minor,currency,evidence_sets,interaction
  provenance.json seed, config, причинные изменения (строки до/после), журнал отвлекающих случаев
```

Форматы значений:

- Время записывается в ISO-8601 со смещением.
- Деньги хранятся целыми минимальными единицами, показатель разрядности валюты указан в
  manifest: JPY 0, KWD 3, остальные 2.
- Курсы хранятся десятичными строками.
- Отсутствующие ссылки записаны как явный `null` (в CSV это пустое поле).
- Все строки ledger ведутся в базовой валюте. Сравнивать суммы в разных валютах можно только
  после конвертации по `fx.csv`.

**Политика компании.** Курс берётся на календарную дату момента сделки в часовом поясе
компании. Если на эту дату курса нет (выходной), берётся последний более ранний. Округление
`ROUND_HALF_UP`, один раз на сумму документа или распределения. AR списывается по курсу счёта,
разница с поступлением денег идёт в `fx_gain_loss`.

## Ошибки, сочетания и отвлекающие случаи

Сначала генерируется согласованная скрытая история компании. Затем она корректно проводится:
это книги «до ошибок». После этого вносятся причинные изменения: переопределение курса, даты
проводки или распределения либо лишний документ. Ошибочная книга строится теми же функциями
проводки. Каждый тип ошибки и каждый сценарий настраиваются независимо через `config.errors` и
`config.interactions`. Случайность разделена на независимые потоки, поэтому включение ошибки
не меняет остальную компанию.

| тип | причинное изменение | affected_ids | сумма | доказательства |
|---|---|---|---|---|
| `duplicate_invoice` | счёт внесён дважды, поздняя копия проведена в AR и выручку | поздняя копия | AR копии | doc оригинала + doc копии |
| `payment_allocation` | часть или весь кредит AR по ссылке платежа ушли в `unapplied_cash` | платёж, счёт | недоразнесённая сумма | doc платежа + строка unapplied |
| `fx_conversion` | курс на неверную дату: соседний рабочий день, срок оплаты или «дата на бумаге» без учёта пояса | счёт или платёж | модуль разницы | doc + строка AR, revenue или cash |
| `period_cutoff` | счёт следующего периода проведён задним числом или прочитан без смещения | счёт | проведённый AR | doc + строка AR или revenue |

**Взаимодействующие сценарии** (каждый даёт две связанные ошибки на одном документе):

- `fx_invoice_with_partial_payment`: счёт в валюте проведён по неверному курсу, а его оплата
  разнесена частично. Сумма недоразнесения считается по верному курсу счёта, поэтому без
  исправления FX-ошибки вторую ошибку правильно не оценить.
- `partial_fx_payment_at_boundary`: частичный платёж в другой валюте в последний день периода.
  Смещение документа сдвигает «дату на бумаге», и курс взят по ней.

**Чистые компании и корректные отвлекающие случаи:**

- законные частичные оплаты и оплаты одного счёта двумя платежами;
- платежи сразу по нескольким счетам;
- платежи без ссылок (законный `unapplied_cash`) и возвраты по ним;
- законные повторяющиеся суммы (тот же клиент и сумма, другой заказ);
- счета у границ периода со смещением, которое «переносит» дату;
- счета следующего периода в выгрузке документов, корректно не проведённые;
- выходные без курса.

Между эпизодами варьируются имена, ID (хеш с солью), порядок строк, суммы, базовая и
иностранные валюты (USD, EUR, GBP, KZT, CHF, CNY, JPY, KWD), часовые пояса, периоды и сочетания
ошибок.

## Matcher и награда

Код открыт в `auditgym/matcher.py`.

**Нормализация.** Тип приводится к нижнему регистру, ID и валюта к верхнему, пробелы
обрезаются. `affected_ids` сравниваются как множества, сумма сравнивается по модулю.

**Допуск суммы:** `max(1, ceil(0.0005 × expected))` минимальных единиц.

**TP** засчитывается при совпадении типа, канонических `affected_ids`, валюты и суммы в
допуске, если среди `evidence_ids` есть хотя бы один полный допустимый набор доказательств.

**Сопоставление.** Строится максимальное взаимно однозначное паросочетание (алгоритм Куна).
При равных вариантах выигрывает более ранний вывод. Несопоставленные и повторные выводы
считаются FP, пропуски считаются FN.

**Метрики:** `P = TP/(TP+FP)`, `R = TP/(TP+FN)`, `F1 = 2TP/(2TP+FP+FN)`. При пустом эталоне и
пустых выводах F1 = 1; если эталон пуст, а выводы есть, F1 = 0.

**Терминальная награда:** `clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)`, где
inspection_steps означает шаги до отправки. Неверная структура `findings.json` даёт −1.
Текст `explanation` на награду не влияет.

Тесты (`tests/test_reward.py`) показывают, что:

- полный верный ответ на ошибочных книгах лучше молчания (+1 против −1);
- молчание на чистых книгах лучше ложных обвинений;
- дубли выводов не дают выгоды;
- атака «пометить всё» даёт F1 < 0,2;
- 40 лишних шагов стоят 0,08, то есть меньше одной найденной ошибки;
- угаданные ID, неполные доказательства, чужая валюта, неверная сумма, повторная отправка,
  неверная структура и тайм-аут дают ожидаемый результат.

## Базовые политики (`auditgym/policies`)

- **random_explorer**: случайные действия с фиксированным seed, затем 0–3 случайных вывода.
- **naive_reconciler**: «простая сверка». Берёт дату из строки как есть, требует точную дату
  курса, ищет дубли по сумме и считает любой `unapplied_cash` ошибкой.
- **flag_all**: атака «пометить всё».
- **oracle**: получает эталон от харнесса, а не из наблюдений, и проверяет максимум награды.
- **scripted_auditor**: наша скриптовая политика для демо. Читает все таблицы (около 14 шагов)
  и сверяет их по опубликованной политике через `auditgym/analysis.py`. F1 = 1 на всех
  эпизодах: это доказательство, что каждая ошибка решаема по доступным записям.

## Честные ограничения

- Награда не доказывает пригодность для реального аудита. Это программная задача, а не
  аудиторское заключение. Все компании, люди и деньги вымышлены.
- Модель учёта упрощена: только дебиторская задолженность, без НДС, кредиторки и переоценки
  остатков. Ошибка отнесения к периоду моделируется только в одну сторону (ранняя выручка).
- Скриптовый аудитор решает среду на 100 %, потому что реализует опубликованную политику
  буквально. Для LLM-агента трудности в другом: бюджет шагов, часовые пояса, правило «последний
  курс не позже», порядок округления, отличие отвлекающих случаев от ошибок. Мы не заявляем об
  улучшении какой-либо модели: обучение весов не проводилось.
- Режим `eval` в одном процессе работает по принципу доверия. Строгая изоляция обеспечивается
  серверным режимом (отдельный процесс).
