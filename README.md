# AuditGym: RL-среда для ИИ-аудитора

**Трек FinTech, Genesis Hackathon 2026. Команда Tech Jacket.**

Воспроизводимый симулятор для дообучения моделей финансового аудита. Генератор создаёт
синтетическую компанию за один отчётный период: книгу проводок, счета, платежи и курсы. В эти
данные внесены скрытые ошибки с записанным причинным изменением. Агент исследует записи через
узкий набор инструментов и отправляет выводы с доказательствами. Оценщик в отдельном процессе
сопоставляет выводы с эталоном и выдаёт терминальную награду.

Ядро написано на чистом Python 3.11 и использует только стандартную библиотеку. Сеть, GPU и
платные API не нужны. Один эпизод генерируется примерно за 0,05 с.

> **Жюри:** пошаговая инструкция «свои seed, свои политики, свой секрет, свои преобразования
> файлов» лежит в [`docs/JURY.md`](docs/JURY.md).

## Запуск одной командой

```bash
# Docker (официальная проверка без сети)
docker build -t auditgym:1.0.0 .
docker run --rm --network none --cpus 2 --memory 4g auditgym:1.0.0

# или локально (Python 3.11+)
pip install -r requirements.txt
python -m auditgym check
```

Команда `check` завершается с кодом 0 только при полном успехе. Она выполняет четыре шага:

1. **`pytest`.** 126 тестов: контракт, награда, генератор, изоляция, интерфейс для жюри и
   независимый red-team набор атак.
2. **Валидация данных и эталона** для всех 40 эпизодов train, dev и holdout_example. Проверяется:
   - бухгалтерские равенства до и после ошибок;
   - ноль расхождений в книгах до ошибок;
   - каждая объявленная ошибка воспроизводится из открытых записей;
   - сумма пересчитывается только по записям одного набора доказательств;
   - схемы;
   - SHA-256 отпечаток всех данных совпадает с `configs/FINGERPRINT`.
3. **Четыре базовые политики и наш скриптовый аудитор** на 20 эпизодах в духе закрытого набора:
   5 чистых, 5 с взаимодействующими ошибками, 10 смешанных. Работают три процесса: оценщик,
   политика и харнесс.
4. **20 парных проверок.** Повтор seed и действий даёт ту же траекторию. Смена всех ID и порядка
   строк сохраняет эталон и награду.

Отчёт сохраняется в `reports/check_report.md` и `.json`.

| команда | что делает |
|---|---|
| `python -m auditgym demo` | скриптовая политика проходит эпизод шаг за шагом (запись: `reports/demo_output.txt`) |
| `python -m auditgym evaluate --split dev` | P, R, F1, возврат, шаги, время и разбор ложных выводов для политик |
| `python -m auditgym run --policy pkg.mod:Class --seed 5` | один эпизод любой политикой, траектория через `--trajectories` |
| `python -m auditgym grade --truth t.json --findings f.json` | оценить готовый findings.json |
| `python -m auditgym export` | 10 train и 10 dev эпизодов в `episodes/`, файлы оценщика в `grader_data/` |
| `python -m auditgym trajectories` | `trajectories/trajectories.jsonl` (режим train) |
| `python -m auditgym serve --episodes hidden.json` | изолированный сервер среды и оценщика (JSON-строки) |
| `python3 independent_check/verify.py` | независимая проверка выгруженных эпизодов (не импортирует пакет) |

## Контракт среды

```python
from auditgym import AuditEnv
env = AuditEnv(mode="train")              # "eval": награда и диагностика остаются у оценщика
obs, info = env.reset(seed=1, config={"errors": {"fx_conversion": 2}})   # или options={"config": ...}
obs, reward, terminated, truncated, info = env.step(
    {"tool": "list_records", "args": {"table": "ledger", "cursor": None, "limit": 50}})
```

Контракт JSON-совместимый, в стиле Gymnasium. Формат описан схемами: `schemas/action.schema.json`
и `schemas/observation.schema.json`.

**Первое наблюдение** содержит задачу, manifest, краткую политику (`policy.json`), список
инструментов и остаток бюджета.
**Наблюдение шага** имеет вид `{step, steps_remaining, tool, result, error}`. В нём только
запрошенные записи или результат, либо ограниченная ошибка `{code, message}` длиной до 200
символов.

| действие | аргументы | результат |
|---|---|---|
| `list_records` | `table` ∈ ledger, invoices, payments, fx; `cursor`; `limit` от 1 до 50 | `records`, `total`, `next_cursor` (стабильный `table@offset`) |
| `get_record` | `table`, `id`: row_id, invoice_id, payment_id, doc_id или `DATE:SRC:TGT` для fx | `record` |
| `get_document` | `doc_id` | `doc_type`, `document` |
| `calculator` | `expression` | `value`. Только десятичная арифметика: `+ - * / // % **` (степень ≤ 12), скобки; константы до 30 цифр; результат от 1e−30 до 1e30 |
| `submit` | `findings` = `{episode_id, findings:[...]}` | `{accepted}` без подсказок о правильности; эпизод завершается |

Правила эпизода:

- **Бюджет:** 100 шагов, отправка тоже считается. `submit` даёт `terminated=true`. Исчерпанный
  лимит шагов или 60 секунд дают `truncated=true` и оцениваются как **пустой ответ**. На чистых
  книгах это верный ответ, на ошибочных даёт −1.
- **Ошибки:** неизвестные ID, таблица, курсор, действие или неверные аргументы возвращают
  ограниченную ошибку и тоже расходуют шаг.
- **Награда во время исследования равна 0.** В режиме `train` терминальная награда и метрики
  возвращаются политике. В режиме `eval` политика получает 0 и пустой `info`.
- **Доступ:** записи отдаются копиями только для чтения. Shell, SQL, файловой системы и
  интернета нет.
- **Воспроизводимость:** одинаковые seed, config, версия, секрет оценщика и действия дают
  одинаковые записи, переходы и награды. `reset` полностью изолирует эпизод.

### Изоляция оценщика

- **Три процесса.** `serve` держит среду, эталон и seed. `policy-worker` держит политику и
  получает только наблюдения. Харнесс пересылает между ними сообщения. Seed передаётся серверу
  файлом (`--episodes`), `reset` возможен только по индексу.
- **Секрет оценщика `AUDITGYM_SECRET`** подмешивается во все потоки случайности, ID и
  `episode_id`. Без секрета небольшой seed можно подобрать перебором по публичным ID (это
  показал наш red-team). Поэтому закрытый прогон без секрета не запускается. Открытые сплиты
  собраны с публичным секретом по умолчанию.
- **Эталон** получает только oracle из списка оценщика (`--oracle-policies`), а не политика,
  объявившая себя oracle. Итог пишется в журнал оценщика.

## Данные эпизода

Эпизод описывает одну компанию за один отчётный период (месяц): 260–620 проводок (до 2 000 при
шумных расходах), 70–195 документов и от 0 до 12 ошибок.

```
episodes/<split>/<name>/
  manifest.json   schema_version, episode_id, base_currency, currency_exponents, period_start/end
                  (end исключительно), timezone, counts, rounding, synthetic: true
  ledger.csv      row_id,timestamp,account,debit_minor,credit_minor,currency,entity_id,invoice_id,payment_id
  invoices.jsonl  doc_id,invoice_id,entity_id,issued_at,due_at,currency,total_minor,line_items
  payments.jsonl  doc_id,payment_id,timestamp,currency,amount_minor,invoice_refs
  fx.csv          date,source_currency,target_currency,rate
  policy.json     дата курса, граница периода, округление, правила отчётности и доказательств, допуски
grader_data/<split>/<name>/      ← закрыто: агент не видит
  truth.json        issue_id,type,affected_ids,expected_amount_minor,currency,evidence_sets,interaction
  provenance.json   seed, config, причинные изменения (строки до/после), журнал ловушек
  ledger_before.csv книги до внесения ошибок
```

**Форматы.**
- Время записывается в ISO-8601 со смещением.
- Деньги хранятся целыми минимальными единицами, показатель разрядности указан в manifest.
- Курсы хранятся десятичными строками.
- **Отсутствующие ссылки — явный `null`.** В JSONL это литерал `null`. В CSV это пустое поле
  (своего null в CSV нет); загрузчик и среда превращают его в `null`.
- Все строки ledger ведутся в базовой валюте. Сравнивать разные валюты можно только после
  конвертации по `fx.csv`.

**Политика компании.** Курс берётся на календарную дату момента в часовом поясе компании; если
курса нет (выходной), берётся последний более ранний. Округление `ROUND_HALF_UP`, один раз на
сумму документа или распределения. AR списывается по курсу счёта, разница идёт в `fx_gain_loss`.

## Ошибки, сочетания, ловушки

Сначала генерируется согласованная скрытая история, затем она корректно проводится: это книги
«до ошибок». Затем вносятся причинные изменения: переопределение курса, даты проводки или
распределения либо лишний документ. Ошибочная книга строится теми же функциями проводки. Каждый
тип и сценарий настраиваются независимо (`config.errors`, `config.interactions`).

| тип | причинное изменение | affected_ids | сумма | набор доказательств |
|---|---|---|---|---|
| `duplicate_invoice` | счёт внесён дважды, копия проведена | поздняя копия | AR копии | оба doc + строка AR копии |
| `payment_allocation` | часть или весь кредит AR по ссылке ушли в `unapplied_cash` | платёж, счёт | недоразнесённое | doc платежа и счёта + строка unapplied (+ строка AR, + ключ курса) |
| `fx_conversion` | курс неверной даты: соседний день, срок оплаты, «дата на бумаге» | счёт или платёж | модуль разницы | doc + строка AR, revenue или cash + ключ курса `DATE:SRC:TGT` |
| `period_cutoff` | счёт следующего периода проведён задним числом или прочитан без смещения | счёт | проведённый AR | doc + строка AR или revenue |

**Взаимодействующие сценарии:**
- `fx_invoice_with_partial_payment`: сумма недоразнесения считается по верному курсу счёта;
- `partial_fx_payment_at_boundary`: частичный валютный платёж в последний день, курс взят по
  «дате на бумаге».

**Ловушки:**
- законные частичные, разбитые и многосчётные платежи;
- платежи без ссылок и возвраты;
- повторяющиеся суммы с разными номерами заказа;
- счета у границы периода в чужом поясе;
- непроведённые счета следующего периода;
- выходные без курса;
- чистые компании.

**Что варьируется:** имена, ID (хеш с секретом), порядок, суммы, 8 валют, 8 поясов, периоды и
сочетания ошибок.

## Matcher и награда

Код открыт в `auditgym/matcher.py`, формат ответа описан в `schemas/findings.schema.json`.

- **Нормализация.** Тип: strip + lower. ID и валюта: strip + upper. `affected_ids` сравниваются
  как множество, сумма по модулю.
- **Допуск суммы:** `max(1, ceil(0.0005 × expected))` минимальных единиц.
- **TP:** совпали тип, канонические ID, валюта и сумма в допуске, и в `evidence_ids` есть хотя
  бы один полный допустимый набор.
- **Неоднозначность:** максимальное паросочетание (алгоритм Куна); при равенстве побеждает
  более ранний вывод. Повторы и несопоставленные выводы считаются FP, пропуски FN.
- **Награда:** `clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)`, где inspection_steps — шаги до
  отправки. Текст `explanation` на награду не влияет.
- **Неверная структура (−1):** не объект `{episode_id, findings}`, лишние ключи, чужой
  episode_id, больше 30 выводов, у вывода не ровно 6 полей, неизвестный тип, сумма не целое,
  валюта не из 3 символов, пустые или больше 30 `affected_ids`, больше 10 `evidence_ids`,
  `explanation` длиннее 1000 символов.

Тесты (`tests/test_reward.py`, `tests/test_redteam.py`) показывают все свойства из кейса:
- полный ответ лучше молчания на ошибочных книгах;
- молчание лучше ложных обвинений на чистых;
- дубли бесполезны;
- «пометить всё» даёт F1 < 0,2;
- 40 шагов стоят 0,08;
- угаданные ID, неполные доказательства, валюта, повторная отправка, неверный ввод и тайм-аут
  работают как ожидается.

## Базовые политики и адаптеры

- `random_explorer` — случайные действия с фиксированным seed.
- `naive_reconciler` — «простая сверка»: дата из строки, точная дата курса, дубли по сумме,
  любой `unapplied_cash` считается ошибкой.
- `flag_all` — атака «пометить всё».
- `oracle` — получает эталон только от оценщика.
- `scripted_auditor` — наша политика для демо: читает все таблицы примерно за 14 шагов и сверяет
  их по опубликованной политике.

Своя политика — класс с методами `reset(observation, info)` и `act(observation) → action`,
подключается как `--policy pkg.module:Class`. Пример: `examples/my_policy.py`. Подробности в
`docs/JURY.md`.

## Честные ограничения

- Награда не доказывает пригодность для реального аудита. Это программная задача, все компании
  и деньги вымышлены (`manifest.synthetic = true`).
- Модель учёта упрощена: только дебиторская задолженность, без НДС, кредиторки и переоценки
  остатков. Ошибка периода моделируется только как ранняя выручка.
- Скриптовый аудитор решает среду на 100 %, потому что реализует опубликованную политику
  буквально. Это доказывает решаемость, но не измеряет сложность для языковых моделей.
  Обучение весов не проводилось, улучшений мы не заявляем.
- Секретность закрытого прогона держится на `AUDITGYM_SECRET`: без него небольшой seed
  подбирается перебором. `AuditEnv` в одном процессе с политикой работает по принципу доверия.
  Строгая изоляция — это `evaluate` и `serve` (отдельные процессы).
- Правило округления ROUND_HALF_UP на сгенерированных суммах почти никогда не попадает ровно на
  .5. Базовый образ Docker закреплён по тегу, а не по дайджесту.
